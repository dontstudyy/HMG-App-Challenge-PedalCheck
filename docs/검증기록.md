# 검증 기록

Pleos Connect 에뮬레이터(AVD, 화면 2560×1440, density 160)에서 확인한 결과입니다. 확인하지 못한 것은 "미확인"으로 적었습니다.

## 단계 0. 확인 실험 (2026-11-15)

| 항목 | 결과 | 비고 |
|---|---|---|
| `PARKING_BRAKE_ON`(0x11200402) 읽기 | **읽힘, 값은 항상 `false`** | `getBooleanProperty`와 구독 모두 성공. 앱 권한 추가 없이 읽힘 |
| 이 값을 바꾸는 Virtual Console 조작 | **찾지 못함** | `ParkingBrake`·`ElectronicParkingBrake`·`AutoHold` 텔테일(`PUT /vehicle/telltales/simulator?type=…&state=On`)을 켜도 값이 바뀌지 않음. 텔테일은 별도 벤더 속성(0x21410900)으로 가는 것으로 보임. 기어 P/D, 속도 변경도 영향 없음 |
| → 결정 | 실행 조건은 **"기어 P, 정차" 2개**. 주차 브레이크는 화면에 "확인할 수 없어요"로 표시하고 조건에서 제외 | 설계서 B2 대체안. 값이 바뀌는 환경이 확인되면 `GateConfig.parkingBrakeUsable`만 켜면 됨 |
| 정차 판정 | 통과 | 속도 3km/h → 0.83m/s로 수신(0.3m/s 초과 = 정차 아님), 0 → 0.0. 기어 D → 주행 규제 ON |
| 기어 D 반응 시간 | 기어 이벤트 후 **156ms**에 주행 규제 ON, 앱은 기어 이벤트 즉시 중단. P 복귀 시 규제 OFF 10ms | 로그 `STATE …` (같은 시계 간격) |
| `brake`만 보내는 PUT | 가능 | `PUT /vehicle/controls?brake=100` / `brake=0` (다른 값은 건드리지 않음) |
| Virtual Console 연결 | 웹페이지 없이 `POST /browser/session?client=ID`를 1초마다 보내면 제어됨 | `tools/key_bridge.py`가 이 하트비트를 함께 보냄 |
| 화면 | 2560×1440, density 160. 앱 창은 차량 상태 패널을 뺀 약 1680×1210px | 앱은 화면 폭이 1280dp가 되도록 밀도를 맞춰 그림 |
| 브레이크 왕복 20회 (REST 직접) | **20/20 수신, 뗌도 20/20, 연속 중복 0** | 누름→뗌 교대 40개 이벤트. 키보드(스페이스바) 경유 측정은 **미확인** |
| `withFrameNanos` 시각 로그 | `SIGNAL_ON t=<프레임 시각 ns>` 로그 출력됨 | 프레임 시각과 리스너 시각이 같은 시계(`System.nanoTime()`)임을 코드로 보장. 실제 표시 지연 크기는 **미측정** |

### 스페이스바 입력 (2026-11-15, AVD 재부팅 후)

앱이 스페이스바를 직접 받아 Virtual Console로 보냅니다(`input/PedalKeyRouter`). 물리 키보드가 아니라 `adb shell input keyevent 62`로 같은 `KeyEvent`를 보내 확인했습니다. 앱 로그의 `BRAKE`는 Pleos 브레이크 리스너가 받은 이벤트입니다.

| 확인 | 결과 |
|---|---|
| 길게 누름(`--longpress`) 20회, Virtual Console 연결됨 | **20/20 수신, 뗌도 20/20, 연속 중복 0, 대비 경로 전환 0.** 누름→뗌 간격 397~432ms |
| 누름과 뗌이 거의 동시(`keyevent 62`) 20회 | **19/20.** 한 쌍이 빠짐. 누름·뗌이 수 ms 안에 연달아 가면 Virtual Console 쪽에서 합쳐지는 것으로 보이며, 사람이 누르는 속도(수십 ms 이상)에서는 나타나지 않음. 사람 손 확인은 아직 |
| Virtual Console 하트비트가 끊긴 상태 | 요청 실패 → `KEYS fallback direct` 로그, 직접 입력으로 측정 가능. 측정 화면의 "직접 입력 중" 표시는 화면으로 확인하지 못함 |

물리 키보드로 직접 20번 누르는 확인은 사용자 실행이 필요합니다. `tools/key_bridge.py`(PC 전역 키)는 선택 사항으로 남겨 두었습니다.

## 단계 1~3 동작 확인 (에뮬레이터, 2026-11-15)

사람 손이 아니라 `SIGNAL_ON` 로그를 보고 지정한 지연 뒤에 Virtual Console로 브레이크를 눌러 주는 스크립트로 확인했습니다. 이 방식의 반응시간은 지정한 지연 + 약 35~45ms(REST 전달)이며 **사람의 반응속도가 아닙니다**. 시연 기준선 근거로 쓰지 않습니다.

| 확인 | 결과 |
|---|---|
| 한 세션 완주 (빨강 5 + 초록 1) | 통과. 정상 5회 622/649/648/692/719ms → 양 끝 제외 → 평균 663ms (화면 0.66초, 1회·5회 "평균 제외" 표시) |
| 초록 참기 | `HELD`로 판정, 결과 화면 "초록 참았어요" |
| 판정 연출 | 제대로 밟음·참기 성공: 초록 화면 테두리와 글로우, 원 둘레 초록 링. 부정 출발·너무 빠름·초록에서 밟음: 빨간 테두리·글로우·링, 화면과 원이 한 번 약하게 떨리고(0.6초) 빨간 진동선이 퍼졌다 사라짐. 놓침은 연출 없음. 캡처로 확인(켜짐 → 유지 → 꺼짐, 깜빡임 없음). 수치는 `ui/FeedbackFx.kt` |
| 연출 초기화 | 연출이 판정 화면(1.0초)이 끝난 뒤에도 남던 문제를 고쳤다(애니메이션이 판정 상태에 묶여 중간 값에서 취소됨). 이제 모든 연출이 1.0초 안에 끝나고, 다음 스텝이 시작되면 기본 상태로 돌아간다. 맞춘 뒤·초록에서 틀린 뒤 다음 "기다리세요" 화면을 캡처해 테두리가 없는 것을 확인 |
| 초록에서 밟음 | `WRONG_PRESS`로 판정, 회차는 넘어감 |
| 신호 전에 밟음 | `FALSE_START`, 같은 회차 다시 |
| 측정 중 기어 D | 중단, P 복귀 후 "측정을 멈췄어요 · 기어가 P에서 바뀌었어요 · 기록하지 않았어요" (기어 D 동안은 OS가 앱 화면을 덮음) |
| 기준선 없음 | 결과 화면 "기준선 만드는 중 1/5", 비교 문구 없음 |
| 시연 기준선 600ms, 오늘 721ms | "평소보다 20% 느려요", "시속 60km라면 2.0m 더 가서 멈추는 셈이에요", 쉬어 가기 문구, 평소/오늘 막대 |
| 앱 강제 종료 후 재실행 | 기록 2건과 시연용 기준선 유지 |
| 중단된 세션 | 기록에 남지 않음 |

### 사람이 키보드로 잰 5세션 (2026-11-15, 시연 기준선의 근거)

설계서는 10세션이지만 5세션으로 줄였습니다(앱이 기준선을 만드는 최소 개수). 물리 키보드 스페이스바로 직접 잰 세션이며, 같은 날 스크립트로 만든 세션(자동 응답, 반응이 6ms 안에 모임)은 뺐습니다.

| 시각 | 세션 평균 | 정상 반응(ms, 회차 순) |
|---|---|---|
| 21:14 | 380 | 336, 337, 391, 463, 413 |
| 21:48 | 328 | 935, 347, 311, 293, 327 |
| 21:49 | 374 | 1067, 299, 423, 363, 335 |
| 21:57 | 373 | 1144, 406, 357, 356, 329 |
| 21:57 | 382 | 356, 353, 508, 409, 382 |

- **세션 평균의 중앙값 374ms**, 범위 328~382ms, 표준편차 20ms.
- 시연 기준선을 374ms(앱 표시 0.37초, "시연용")로 지정했습니다. 목업의 0.60초와 달라서, 시연 화면의 비교 숫자는 목업(3%, 18%)과 다르게 나옵니다. 목업 숫자는 단위 테스트로 증명합니다(설계서 A4).
- 5세션 중 4세션의 첫 회차(또는 마지막 회차)에서 0.9~1.1초대의 큰 값이 나왔고, 평균에서는 양 끝 제외로 빠졌습니다.
- 5세션 모두 초록 신호에서 한 번 이상 밟았습니다(잘못 밟음 4건, 참기 성공 1건 — 직접 시험한 것인지 의도치 않은 입력인지는 미확인).
- 앱 DB에는 스크립트로 만든 세션(id 1~4, 6)이 함께 남아 있습니다. `지금 기록으로 기준선 만들기`는 쓰지 말고, 지금처럼 `기준선으로 지정`으로 정한 값을 씁니다.

### 미확인

- 물리 키보드로 직접 누르는 스페이스바 20회, 대비 경로의 "직접 입력 중" 화면 표시
- 실제 소리 청취 (효과음 5개와 TTS는 코드로 연결됐고 크래시 없음만 확인)
- 시연 영상 녹화: 앱 화면 녹화는 하지 못했고, 제출 영상은 목업 영상
- 클린 클론에서의 전체 빌드(`git clone` 후 `testDebugUnitTest assembleDebug assembleRelease`) 확인
- 사람이 직접 한 시연 순서(약 2분) 전체 리허설

### release(R8 최적화) 빌드 · 제출용 서명 APK (2026-11-15)

- `assembleRelease`로 제출용 키(저장소 밖 보관)로 서명한 APK를 만들고 `apksigner verify`로 서명을 확인했습니다(인증서 CN=PedalCheck). 파일: `apk/정통윤_PedalCheck_release.apk`(약 26MB).
- 깨끗한 AVD(콜드 부팅 직후, 앱 기록 없음)에 `adb install -g`로 설치해 실행하고, 한 세션(빨강 5 + 초록 1)을 끝까지 쟀습니다. 크래시·`IllegalAccessError` 없이 결과 화면(0.46초, "기준선 만드는 중 1/5", 양 끝 값 "평균 제외", 초록 "참았어요")까지 나왔습니다. 이 측정은 신호를 보고 브레이크 신호를 보내는 스크립트로 한 것이라 사람 반응 값이 아닙니다.
- 단계 5 기능 중 release에서 직접 눌러 확인한 것은 위 측정까지입니다. 시연용 기록·추이·가족·3개월 안내, Gleo, 출발 전 제안은 debug 빌드에서 확인했습니다(release에는 길안내 시험용 수신기가 없음).
